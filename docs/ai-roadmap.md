# 非同期・時間制約型AI 強化ロードマップ

最終更新: 2026-09-15

本書は「このゲーム専用の最強AI」を作るための調査結果と実装計画である。
ゲームルールは `docs/game-spec.md` と既存実装（`src/game/`）を唯一の正とする。
AI実装の都合でルールを変更しない。

---

## 1. 調査結果（現状把握）

### 1.1 AIが取得可能な State

ルール層の公開窓口は `toPublicMatchState()`（`src/game/match.ts`）。

| 項目 | 型 | 備考 |
|------|-----|------|
| `board` | `Cell[][]` 10×10 | 石配置 |
| `cooldowns.black` / `.white` | number (ms) | 双方の残りクールタイム |
| `elapsedMs` | number | 試合開始からのゲーム内時間 |
| `remainingMatchMs` | number | 残り試合時間（180000 - elapsed） |
| `phase` | `'playing' \| 'paused' \| 'finished'` | |
| `simultaneousPriority` | `Stone` | 同時着手の優先側 |
| `endReason` / `outcome` | | 終局後のみ |

公開状態に含まれない内部状態（AIが直接は見られない）:

- 相手の**判断待ち残り**（`cpuThinkRemainingMs`）
- 相手の**無操作タイマー残り**（`idleRemainingMs`）

ただしこの2つは、**盤面変化時刻と相手のクールタイムから推定できる**（1.4 参照）。
AIの内部状態としては推定値を持つ。

`simultaneousPriority` は仕様 2.3.3 により学習用観測には含めない（プレイヤーUIに出していない）。
本AIもこれに従い、観測から除外する。

### 1.2 時間状態の表現と「非同期性」の実体

計測して確認した時間パラメータ（`src/game/config.ts`）:

| 値 | 意味 |
|----|------|
| `stepMs = 50` | ゲーム内時間の固定ステップ |
| `cooldownMs = 700` | 着手成功後の待ち時間 |
| `cpuThinkDelayMs = 500` | CPU側の判断待ち（プレイヤーには無い） |
| `idleAutoMoveMs = 3000` | 着手可能なのに置かないと強制ランダム着手 |
| `matchDurationMs = 180000` | 試合時間 |

**確認済みの重要な挙動**（`tickThinkGate` を直接叩いて計測）:

| 条件 | ready になる時刻 |
|------|------------------|
| 盤面変化なし | 着手可能になってから **450ms** |
| 途中 t=200ms で盤面変化 | **650ms**（変化時刻 + 450ms） |
| 300ms ごとに盤面変化 | **2250ms**（最後の変化 + 450ms） |
| 無操作タイマー（固定シグネチャ） | **2950ms**（盤面変化では伸びない） |

ここから、このゲームの時間構造は次のとおり。

1. 1手の標準周期は `700 + 500 = 1200ms`。実測では「着手 → cooldown 0 が 700ms 後 → その 450ms 後に ready」なので、
   盤面が動かなければ **1150ms 周期**。
2. **相手が自分の判断待ち（500ms窓）の中で着手すると、自分の判断待ちがリセットされる。**
   つまり相手の着手は自分の着手タイミングを後ろにずらす。これが非同期性の中核。
3. ただしリセットは無限には効かない。着手可能のまま 2950ms 経つと**強制ランダム着手**になる。
   よって「判断待ちリセットによる時間攻撃」の上限は約 2950ms。
4. 盤面は空き 84 マスしかなく、双方 1150ms 周期なら約 50 秒で埋まる。
   **`time_up`（180秒）はほぼ発生しない。** 残り試合時間より「あと何手打てるか」の方が支配的。
5. 片方が合法手を失うと、その側はクールタイム消化しても行動できず、相手が**連続着手**できる。
   これが盤面価値と時間価値の交換が生じる主要な局面。

→ AIが扱う時間状態は「残り時間」ではなく、
**「自分と相手の次回行動可能時刻の差（テンポ差）」と「判断待ちリセットの有無」** を中心にする。

### 1.3 合法手生成

2系統あり、結果は一致（`strategy.test.ts` で照合済み）。

- ルール層 `listLegalMoves`（`src/game/board.ts`）: `Cell[][]` を走査、配列を確保する。正しさ優先。
- 探索層 `generateMoves`（`src/cpu/strategy/fastBoard.ts`）: 12×12 番兵付き `Uint8Array` +
  空きマス双方向リスト + Zobrist ハッシュ。`doMove` / `undoMove` で確保なし。**探索向けに十分速い。**

### 1.4 Simulator の速度（実測）

`npx tsx` で `runGaMatch`（`src/ga/matchRunner.ts`、ルール層 `stepMatch` 使用）を計測:

| 対戦 | 速度 | 1試合あたり |
|------|------|-------------|
| random vs random | 83.2 games/s | 12.0 ms |
| 遺伝子CPU vs 遺伝子CPU | 11.1 games/s | 90.2 ms |
| 戦略AI(αβ 60k nodes) vs random | 0.4 games/s | 2581 ms |

**これが最大のボトルネック。** 原因は3つ。

1. `stepMatch` が毎ステップ `cloneMatchState` → `cloneBoard`（10×10 配列を毎回複製）
2. 判断待ちの照合に `boardSignature()` が**毎ステップ 100 文字の文字列を構築**
3. 50ms ステップを 1 つずつ回す（既に一部 fast-forward があるが、内側ループは逐次）

AlphaZero系の自己対戦には桁が足りない。Phase 1 で作り直す。

### 1.5 現在のAI実装

| ID | 中身 | 位置づけ |
|----|------|----------|
| `random` | 合法手から一様ランダム | 下限ベースライン |
| `max_flip` | 即時反転数最大 | 貪欲ベースライン |
| `strategy` | **時間状態対応 αβ**（反復深化・置換表・killer/history） | 現行最強クラスの探索 |
| `ga_best` + `ga_g15`〜`ga_g100`（18体） | 36遺伝子 線形評価（12特徴×3フェーズ） | GA育成 |
| `wait` | 常に待機 | テスト用 |

`strategy` は既に非交互手番を扱っている（`selfNextMs` / `oppNextMs` の小さい側が手番）。
ただし **判断待ちリセット（1.2 の 2）はモデル化していない。** 改善余地。

### 1.7 利用可能リソース（実測）

```
CPU: Intel(R) Core(TM) 5 120U / 論理 12 コア
RAM: 16.9 GB
Node: v24.19.0
GPU: CUDA 利用不可（省電力ノート向け内蔵GPU）
```

→ **GPU学習は不可。** 方針は次のとおり。

- ニューラルネットは**純TypeScript + typed array** で実装する。新規依存を追加しない（プロジェクトルール）。
- 規模は「10×10 の小型CNN」に抑える。
- 並列化は Node 標準の `worker_threads`（12コア）で行う。追加依存なし。
- 将来クラウドへ持っていけるよう、自己対戦ワーカーは**シード指定だけで再現**できる形にする。

### 1.8 並列シミュレーションの可能性

- `worker_threads` が利用可能。現状どこも使っていない。
- 1試合は完全に独立（共有状態なし・シード決定的）なので**素直に並列化できる**。
- ネットの重みは `Float32Array` なので `SharedArrayBuffer` でワーカー間共有できる（コピー不要）。

## 2. 設計方針

### 2.1 Game State（探索が持つ状態）

```
AiState =
  盤面（12×12 番兵付き Uint8Array + 空きリスト + Zobrist）
  timeMs                 現在のゲーム内時刻
  cooldown[2]            双方の残りクールタイム
  thinkRemaining[2]      双方の判断待ち残り（相手側は推定）
  idleRemaining[2]       双方の無操作タイマー残り
  boardVersion           盤面世代（判断待ちリセット判定に使う）
  simultaneousPriority   同時着手の優先側（探索内部のみ・観測には出さない）
```

時間情報を落として同一局面として扱わない。置換表キーにもテンポ差を混ぜる。

### 2.2 時間の離散化について

ルール自体が 50ms 固定ステップなので、**50ms がこのゲームの時間精度そのもの**である。
これより粗くしない。これより細かくもしない（ルールに存在しない精度を作らない）。
探索は「次に発生する意思決定イベント」を単位とし、イベント間は解析的にジャンプする。

### 2.3 行動空間

`docs/training-environment.md` に従い 101（100マス + WAIT）。
WAIT は捨てない。1.2 の 3 より、**最大 2950ms まで自発的に待ってテンポをずらす**のは
実在する戦略選択肢だからである。ただし待ちすぎると強制ランダムになる罰がある。

## 3. 実装フェーズ

| Phase | 内容 | 完了条件（勝率/速度で検証） |
|-------|------|------------------------------|
| 1 | イベント駆動 高速シミュレータ | ルール層と**着手列・終局・時刻が完全一致**。random対戦で 10 倍以上高速 |
| 2 | Random / Greedy ベースライン + Arena | Wilson 信頼区間つき勝率、Elo、有意差判定が出る |
| 3 | 時間状態対応 Search（判断待ちリセットを含む） | 現行 `strategy` に勝率で有意に勝つ |
| 4 | 時間イベント型 MCTS | Phase 3 と同条件で勝率比較 |
| 5 | Policy Network | 合法手マスクつき。MCTS の事前確率として機能 |
| 6 | Value Network | 勝率予測。盤面優位/時間優位を区別 |
| 7 | Policy + Value + 時間対応MCTS | Phase 4 に有意に勝つ |
| 8 | 自己対戦データ生成（12ワーカー並列） | 再現可能な JSONL。生成スループット計測 |
| 9 | 自動学習パイプライン | Self Play → Train → Eval → Champion 選抜が無人で回る |
| 10 | 自動評価・Champion 選抜 | 弱くなった世代を自動破棄。Elo 履歴が残る |
| 11 | 並列自己対戦の拡張 | ワーカー数・バッチ推論のスケール確認 |
| 12 | 継続最適化 | 探索パラメータの勝率ベース調整 |

各フェーズで「Loss が下がった」ではなく**実際の対戦勝率**で採否を決める。
改善しなかった手法は採用しない。実験結果は `docs/ai-experiments.md` に追記する。

## 4. 決めたこと・決めていないこと

決めたこと:

- ルール層（`src/game/`）は読むだけ。変更しない。
- 既存CPU（`strategy` / GA 18体）は消さない。比較相手として使う。
- 新規依存を追加しない。NN は純TSで書く。
- 判断待ち 500ms は AI-vs-AI でも双方に課す（`matchRunner` と同じ扱い）。

決めていないこと（ベンチマークで決める）:

- MCTS が αβ より強いか。部分的に αβ を残すか。
- ネットの規模（チャンネル数・ブロック数）。
- 終盤の完全探索に切り替える閾値。
